## 0. What this document is, and is not

**It is** a precise list of the data-layer questions the client cannot answer on its own, so that the affected requirements can be implemented without the client inventing behaviour.

**It is not** a schema proposal. Per the instruction that governs this phase:

- No table names, column names, SQL, RLS policy expressions, API endpoints or data types are invented here **except where the SRS explicitly provides them** (§4.1 entity names and "Atribut Kunci (indikatif)", §4.2 cardinalities, and values named in FR/NFR text).
- Where the SRS is silent, the item is marked **`BACKEND DECISION REQUIRED`** and the question is addressed to the data owner rather than answered.
- Where the client already assumes something (visible in the code), that assumption is **reported as an assumption under test**, not presented as a requirement.

### 0.1 Evidence gap the client cannot close

The client repository contains **no schema, migration, RLS policy, function or API contract artefact**. A repository-wide search finds none. Consequently:
- No data-layer requirement can be confirmed as satisfied from the client side.
- Every "client's current assumption" below is derived from the client's own read/write calls and is **unverified against any backend artefact**.
- Please attach or link the authoritative schema/policy source when answering, so the client can cite it instead of guessing.

### 0.2 Classification legend (used per item, as requested)

| Class | Meaning |
|---|---|
| **REQUIRED BY SRS** | The SRS states the behaviour or the data explicitly (FR/NFR text or §4.1/§4.2). The backend must support it. |
| **IMPLIED TECHNICAL CONTRACT** | The SRS requires an outcome, and the client cannot deliver it without *some* agreeing arrangement whose details the SRS does not fix (e.g. read/write shape, access path). |
| **NOT SPECIFIED BY SRS** | Nothing in the SRS fixes this. Marked **`BACKEND DECISION REQUIRED`** — the client must not assume a default. |

### 0.3 How to answer (response template)

For each item, either answer or explicitly decline. A declined item must remain marked as unassumed in the client — silence will not be treated as consent to invent.
